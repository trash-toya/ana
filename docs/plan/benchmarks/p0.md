# P0 baseline benchmarks (G0 criterion 5)

Machine: 8 cores, 7.5 GB RAM, NVMe; TimescaleDB `timescale/timescaledb-ha:pg17`
(shared_buffers=1 GB, `synchronous_commit=on`) in Docker on the host, client on loopback.
`ingest_batch()` called directly — no API layer (that is P1). Batches are the API's
`MAX_BATCH` = 500 events. Runs: `npm run bench:p0` (`ops/loadtest/p0-bench.mjs`),
raw JSON in `p0-results.json`. Database built from migrations, dropped afterwards,
no schedule/policy jobs (same hermetic setup as the tests).

## Results

| Benchmark | Result |
| --- | --- |
| **Sustained 400 ev/s**, 8 workers, 30 s, 2,000 sessions | target met exactly (400 ev/s); per-call (500-event batch) p50 219 ms, p95 358 ms, p99 394 ms; WAL 0.6 MB/s ≈ **1.5 KB/event** |
| **Burst** (max rate, 2 s, fresh sessions) | **35,750 ev/s** achieved; per-call p50 102 ms, p95 115 ms, max 591 ms |
| **Hot session** (20 workers into ONE session until cap) | 1,761 ev/s into a single session — the guard row serializes writers, as designed; cap held (exactly 5,000 stored) |
| **archive_sessions**, 6,501 sessions | **142.8 ms** (≈ 22 ms per 1,000 rows) after the ctid rewrite; 0 rows left in `sessions_active` |
| **HOT ratio** (sustained+burst+hot run) | `session_guard` 48 % HOT of 83,750 updates; `sessions_active` 46 % of 77,249; `event_dedupe` inserts only |

## Findings and decisions

1. **Archive selection must be ctid-based, not a `USING` self-join.** With
   `DELETE … USING (SELECT … FOR UPDATE SKIP LOCKED)` the planner re-executes the
   locking scan once per candidate row (measured **34 s for 7,000 rows**; even
   `AS MATERIALIZED` still left a 49M-comparison join filter). The shipped form
   selects candidates by `ctid` and gets **0.13 s for 7,000 rows**. Locked-read
   semantics (EPQ re-check of `touch_bucket`) are preserved. Recorded as a note in
   `03-write-path.md`; semantics unchanged, so no deviation row is needed.

2. **Capacity vs blueprint assumption.** The blueprint plans for 100–1,000 ev/s per
   ~100k-session tenant. One 8-core dev container saturates around **33–35k ev/s
   burst**, i.e. ~35× the top target, with p95 under 120 ms per 500-event call. The
   write path is not the bottleneck at planned scale; pool sizing (≤ 8 writer
   connections per instance) and 500-event batches are confirmed. No change.

3. **Chunk intervals confirmed as planned** (`events`/`sessions_history` 1 day,
   `session_stats_15m` 7 days): total WAL for 12k stored events ≈ 18 MB
   (1.5 KB/event — the `events` row, dedupe, guard and session row together), far
   below any pressure point for the 90-day retention window.

4. **HOT ratio ~48 %, not the "nearly all" the blueprint assumes.** Cause is
   understood: `touch_bucket` is part of the `sessions_active_touch` index and
   changes on every write, so those updates can never be HOT by definition; the
   guard's counter updates are HOT whenever page space allows (fillfactor 70).
   Options later (P4, only if bloat shows up in staging): move `touch_bucket` out
   of the index in exchange for a partial index, or add a fillfactor run on the
   autovacuum settings. Not a P0 blocker; revisit with real traffic.

5. **Sustained per-call latency (p50 ≈ 220 ms at 400 ev/s) is dominated by
   `synchronous_commit` fsync on spread-out single-batch commits** — the burst run
   (102 ms p50) shows the calls themselves are faster when commits bunch up. This
   is the expected trade for durability; the P1 API batches per instance so the
   effective commit rate stays low.

Re-run at any time with `npm run bench:p0` (env: `BENCH_SECONDS`, `BENCH_RATE`).
