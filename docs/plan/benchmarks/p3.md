# P3 dashboard benchmarks (P3-6)

Machine: 8 cores, 7.5 GB RAM, NVMe; TimescaleDB `timescale/timescaledb-ha:pg17`
(shared_buffers=1 GB, `synchronous_commit=on`) in Docker on the host, client on
loopback. Runs: `pnpm run bench:p3` (`ops/loadtest/p3-bench.mjs`), raw JSON in
`p3-results.json`. Database built from migrations, dropped afterwards, no
schedule/policy jobs (same hermetic setup as the tests and p0-bench).

Dataset: 2,000 sessions / 10,000 events over a 96 h window through the real
`ingest_batch()` (500-event batches), a second tenant adding cross-tenant volume,
archived, CAGGs materialized, `rollup_daily` run once; 60 live `sessions_active`
rows with fresh touch buckets. Every endpoint measured 50× over HTTP through the
real service (`supertest`), then re-measured under background ingest at 200 ev/s
into fresh sessions (scenario B).

## Results

| Endpoint (steady state)       | p50    | p95          | p99      |
| ----------------------------- | ------ | ------------ | -------- |
| `GET /v1/sessions/:id/replay` | 3.8 ms | 5.3 ms       | 20.6 ms  |
| `GET /v1/metrics/hourly`      | 5.2 ms | 6.6 ms       | 10.2 ms  |
| `GET /v1/metrics/daily`       | 6.2 ms | 7.5 ms       | 21.1 ms  |
| `GET /v1/entry-pages`         | 5.5 ms | 6.3 ms       | 7.4 ms   |
| `POST /v1/funnels` (3 steps)  | 307 ms | **379.3 ms** | 381.7 ms |
| `GET /v1/live`                | 4.4 ms | 5.9 ms       | 12.4 ms  |

| Endpoint (under 200 ev/s ingest load) | p50      | p95      |
| ------------------------------------- | -------- | -------- |
| `hourly`                              | 5.0 ms   | 6.3 ms   |
| `live`                                | 4.2 ms   | 4.7 ms   |
| `daily`                               | 5.6 ms   | 8.8 ms   |
| `funnels`                             | 296.2 ms | 341.0 ms |

Worst p95 across all measurements: **379.3 ms — PASS (target < 500 ms)**.
Ingest load did not degrade the read path (funnel actually sampled slightly lower
under load — noise; rollup reads do not contend with the guard/active-row write
path).

## Findings and decisions

1. **The funnel is the only non-trivial query.** The recursive CTE walks every
   engagement event in the range (≈ 8 k rows here) and costs ~300 ms. At P4
   scale (100 k+ events/day) this approaches the 500 ms budget — candidates:
   a `(tenant_id, name, time)` index, or pre-materialized step counts. Left for
   the P4 performance pass with real-scale data; the current result meets the
   target with headroom, so no change now.
2. **Rollup reads are negligible.** Hourly/daily/entry-pages/live are all under
   9 ms p95 at this dataset size — the G3 rule (never read raw `events` for
   headline metrics) is doing its job: the two rollup-backed endpoints stay flat
   regardless of raw-event volume.
3. **HTTP + auth overhead is ~1–2 ms** (measured: `live` p50 4.2 ms vs the same
   SQL directly at ~2 ms); negligible, keep the simple per-request transaction
   (`BEGIN READ ONLY` + `set_config`) — pooling and RLS in P4 will not change
   the shape.
