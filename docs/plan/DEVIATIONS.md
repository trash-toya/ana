Every row is a deliberate change. A row is only "done" when its covering test exists.
Anything not listed here is implemented as written in the PDF.

| **D20** | `app_owner` and `app_jobs` are `NOLOGIN`. | Both are `LOGIN`. Timescale background tasks refuse `NOLOGIN` owners ("Hypertable owner must have LOGIN permission to run background tasks"), which breaks both the compression/retention policies (owned by `app_owner`) and the scheduler (registered as `app_jobs`). Production restricts these logins with `pg_hba.conf` to the migration/scheduler host only. | The alternative — keeping policies/scheduler under the bootstrap superuser — leaves the background work running as a role that owns nothing and must not exist in production. | Migration test: policies registered and schedulable on the pinned image |
| **D21** | Compression/retention policy jobs are owned by the hypertable owner and the scheduler runs as `app_jobs`; `GRANT`s are issued by the bootstrap role. | Policy jobs are registered under the bootstrap role (LOGIN requirement above); `ingest_batch()` is re-owned by `app_writer` and job procedures by `app_owner` via `ALTER`, but every `GRANT` to `app_ingest`/`app_writer`/`app_jobs` is executed as the bootstrap role. | PostgreSQL 16+ requires the grantor to be able to `SET ROLE` to the grantee; a NOLOGIN/BYPASSRLS definer role cannot be a grantor without superuser membership. The bootstrap role exists only inside the migration runner connection. | Migration test (roles/grants assertions) |
| **D22** | T4 wording: "Same event_id twice in a request with different payloads — first by ord wins; the other is `conflicting_duplicate`." | The per-ID outcome is decided by the **first occurrence only**: the response reports each ID exactly once (response contract), so an in-batch conflicting variant of an ID whose first occurrence stored folds into `accepted` (the client drops the ID either way). In-batch conflicting variants are still counted for rejection metrics via the validation ledger. | Two entries for one ID would violate "every submitted event ID appears in exactly one list"; the wire contract only carries IDs. | Ingest assembly tests: "every submitted ID appears in exactly one list" (services/ingest/test/validate.test.mjs) |

| **D23** | Blueprint SDK ordering: implicit "enqueue then update session" assumption. | The SDK saves the session record with **final counters BEFORE enqueueing any minted event** (P1-5: `saveRecord` after `mintEvent` mutations, before `enqueue`). A kill between the two writes leaves a harmless seq gap, never a durable event the restored record does not know. Restore reconciles `seq` up to `maxQueuedSeq` (test: "kill between session save and enqueue"). | The reverse order persists a durable event whose `seq` the record would re-issue after restart → duplicate seq in one session. | `packages/sdk-web/test/sdk.test.mjs` |
| **D24** | Session record has a single "last" timestamp in the blueprint tables. | The stored record keeps **two** clocks: `last_event_at` (monotonic event time: `max(now, last+1)`, drives per-instance time strictness) and `last_seen_at` (engagement/expiry clock, moved only by non-heartbeat events). Heartbeats advance `last_event_at` but never `last_seen_at` (D16). | One clock cannot satisfy both "strictly increasing per-instance time" and "heartbeats never extend the session": a heartbeat would either repeat a timestamp or extend idle expiry. | SDK tests: heartbeat non-extension + strictly increasing times (packages/sdk-web/test/sdk.test.mjs) |
| **D25** | UUIDv7 collisions within one millisecond. | The SDK mint counter runs in the **first two random bytes** of the UUIDv7 random field, reset per millisecond, so events minted inside one `track()` call (session_start → page_view → event, same ms) keep mint order as localStorage keys (`sa_ev:<id>` sort = enqueue order). | Same-ms UUIDv7s otherwise sort arbitrarily, which can reorder session_start behind page_view in the durable queue and in batch selection. | SDK test: fresh session emits `session_start, page_view, click` in order (packages/sdk-web/test/sdk.test.mjs) |
| **D26** | Compose topology: pgbouncer on host 6432. | Two fixes in `ops/docker-compose.yml` found during P1-6: (a) `LISTEN_PORT=6432` — the edoburu image listens on 5432 by default, so the `6432:6432` mapping hit nothing; (b) `IGNORE_STARTUP_PARAMETERS=statement_timeout` — transaction-mode pooling rejects the ingest pool's startup parameter, killing every connection. | Without (a) nothing on 6432 answers; without (b) `/readyz` 503s and no event is ever flushed. Both are image/defaults mismatches, not topology changes — the 07-operations.md topology (host 6432) is unchanged. | Demo run: `npm run demo` end-to-end (demo/run.mjs); ingest e2e suite through pgbouncer |

| **D27** | Blueprint quota rule: "drop heartbeats first, then oldest events." | Eviction frees **bytes, not slots**: victims are dropped one at a time (heartbeats first, then oldest) until the freed bytes cover the incoming event. Every victim is counted in the pending `sdk_dropped` counter, which is reported through the **normal emit path** on the next flush (normal expiry rules apply; a stale session is not resurrected to carry it) — a report that itself overflows evicts further victims that the next report carries, and the sequence converges. | Freeing a single slot loses the incoming event whenever it is larger than the victim, and under a full store the unreported drop counter would grow forever. | Conformance case "overflow" + web tests (packages/sdk-web/test/conformance.test.mjs) |

| **D28** | Rev 5 §19.4 keeps `source` as event metadata but does not say how a producer is prevented from claiming another source. | `source` is a per-event field; authorization is by API-key kind: an `ingest` (client) key may only submit `source = 'client'` (the default), a `server` key may submit `client`, `server` or `webhook`, and a `dashboard` key cannot ingest at all. A client key submitting another source gets `403 source_not_allowed` for the whole batch (never a partial accept). | Without the key-kind check, any browser holding the public ingest key could forge an authoritative `Order Placed` event, which is exactly what "server-originated events are authoritative" must prevent. | Ingest e2e: client key + `source: server` → 403, nothing stored; server key accepts all three sources |
| **D29** | Rev 5 §19.3 says machine-originated events may have no session but the schema assumed `session_id NOT NULL` everywhere. | `events.session_id` and `events.anon_id` become nullable. Sessionless rows skip `session_guard` (no lock, no cap), skip `sessions_active`/history counters and skip identity stitching; they still go through dedupe and the cap-free insert. Invariant I8 excludes `session_id IS NULL` (a sessionless event has no guard by design). `anon_id` stays required for any event that _does_ carry a session (rejection `missing_anon_id`), because attribution and `sessions_active.anon_id` depend on it. | Fabricating a per-job "session" would pollute session counts, bounce rate and the 5,000-event cap; leaving `anon_id` NOT NULL would force producers to invent a visitor. | T12 (sessionless insert + I8) and ingest validation test (`missing_anon_id`) |
| **D30** | Rev 5 §19.2 requires a bootstrap/resume endpoint separate from ingestion, with races handled, but does not name a storage model. | `session_bootstrap` (tenant_id, session_id, anon_id, user_id, started_at, last_event_at, props) is the bootstrap record; **no analytics rows are created until the first event arrives**. Concurrent bootstraps for the same `(tenant_id, anon_id)` serialize on `pg_advisory_xact_lock` and return the same resumable session. Rotation: idle > 30 min (`last_event_at`), age > 24 h (`started_at`), or a different `user_id` on resume (login/logout switch). The resume response carries `emitted_events` (from `session_guard`) so the server SDK emits `session_start` only when the session has none, and rehydrates the persisted bootstrap `props` for attribution. | Putting bootstrap rows in `sessions_active` would create zero-event ghost sessions that `archive_sessions` later counts as real sessions, inflating session counts and bounce. A separate table also keeps "session lifecycle" and "event delivery" semantically separate, as §19.5 requires. | Ingest session tests: race → one session, idle/age rotation, user switch rotates, `emitted_events` 0 vs >0 |
| **D31** | Ordering contract is `(time, seq, event_id)` with `seq` minted per session by the writer. | Server-SDK events send `seq = NULL` by default (explicit override available). Ordering falls back to `time, event_id`; the DB already documents `seq NULLS LAST`. | A server process cannot know the client's next seq for the same session, so minting one would produce duplicate seq values inside a session and make funnel ordering ambiguous. Server events are timestamp-ordered, which is what the backend actually observed. | Server SDK unit test (seq omitted) + replay ordering test |
| **D32** | Rev 5 §19.4: "use server time for server-originated events; treat client timestamps as untrusted input." | `source = 'client'` keeps the existing correction `t' = t + (received_at − sent_at)`. For `source = 'server'`/`'webhook'` the producer's `time` is used as-is (a webhook must keep the provider's event time), still bounded by the 24 h / 5 min window. Every stored event carries `received_at` separately, so late-arrival analysis never depends on `time` alone. | Applying browser-style skew correction to a backend clock would shift genuinely late webhook times by the sender's delay (`sent_at` is the webhook's send moment, not the provider event moment). Keeping both timestamps preserves the forensic signal. | Ingest validation test: server source time is not corrected; client source is; `received_at` persisted |

## Things we accept as-is and will not "fix"

| Item                                              | Position                                                                                                                                                                                                                                                    |
| ------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| No foreign keys on `events`                       | Correct for an append-only hot path; replaced by periodic integrity checks (I8).                                                                                                                                                                            |
| `event_dedupe` as a plain table with a global key | Correct; it is the only way to be race-free across midnight. Generation tables are a P5 option, not a correction.                                                                                                                                           |
| No `COMMIT` inside job procedures                 | Correct; each run is one bounded transaction and at-least-once execution is idempotent.                                                                                                                                                                     |
| Client-minted session/event IDs                   | Correct; the client is the only component that sees the person leave and return. The embedded UUIDv7 timestamp is never trusted.                                                                                                                            |
| 3-day guard/dedupe retention                      | Correct: 24 h event age + 24 h max session + 1 day margin.                                                                                                                                                                                                  |
| Approximate visitor/user counts                   | Correct and labelled; HLL at 4,096 buckets is ~1.6% error and rollups need the sketch.                                                                                                                                                                      |
| Rate limits in process                            | Correct at the current few-instance scale, but per-key limits are per instance (N× the configured value). Per-session and per-IP limits are exact under consistent-hash routing; per-key limits move to a Postgres counter before more instances are added. |

   function — P0-2 spike decides between CAGG, a per-bucket job, or a maintained table.

   aggregates cannot carry RLS, so `events_15m`/`identity_15m` are exposed only through
   `security_invoker` views that force `tenant_id = app_tenant()` — P4-1 verifies this on
   the pinned version.
3. ~~Whether `events` needs `received_at` for forensics — decide in P0 (adding it later leaves
   historical rows NULL forever).~~ Decided in Rev 5 (D32): `received_at` is a first-class
   column from migration `0015`; the table has no production rows yet.
4. Chunk interval (1 day vs 6 hours) — decided by P0-10 measurements, not by preference.
